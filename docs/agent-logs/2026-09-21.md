### What Was Done
- **Diagnosis & Architecture Design:**
  - Evaluated user request addressing 4 core improvements:
    1. Replace abrupt queue percentage jumps ("jleg-jleg", e.g., 15% -> 50% -> 90%) with granular, continuous sub-stage reporting (params setup, media reference ingestion, prompt injection, live tile generation percentages, and per-card download progress) aggregated smoothly across all rows.
    2. Lock/disable all interactive inputs in the HUD overlay while a batch is executing (sidebar parameters, set params dropdown, sort button, add row button, checkboxes, media slots, prompt textareas), while keeping row container selection active so users can inspect row settings in read-only mode without mutating running state.

- **Granular Monotonic Progress Calculation (`src/core/QueueManager.js`, `src/overlay/FlowHUDHost.js`):**
  - Refactored `QueueManager.processItem()` to report granular progress via `this.onProgress({ itemId, status, percent })`:
    - `injecting`: init/readiness (2%), settings application (5%), media upload/verification (8% to 11%), prompt injection (13% to 15%).
    - `generating`: batch spawning (18%), live multi-tile percentage mapped from 18% to 85% (`18 + Math.round((pct / 100) * 67)`).
    - `downloading`: mapped sequentially per downloaded card from 85% to 99% (`85 + Math.round(((idx + 1) / totalCards) * 14)`).
    - `completed`: 100%.
  - Implemented `FlowHUDHost.calculateCumulativeProgress(activeItemId, activeStatus, activeItemPercent)`:
    - Accumulates completed items (100% each), active item's real-time sub-percentage, and pending items (0%), divided by total row count.
    - Guaranteed strictly monotonic advancement via `Math.max(this.lastOverallPercent || 0, calculated)` to eliminate percentage reversals or stuttering.
