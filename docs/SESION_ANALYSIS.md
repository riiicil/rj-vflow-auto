## 1. Project Overview

**RJ V-Flow Auto** is a Chrome extension (Manifest V3) that automates image and video generation on [Google Labs Flow](https://labs.google/fx/tools/flow/). The extension:

- Reads a list of prompts from the side panel
- Configures generation settings (mode, aspect ratio, output count, model)
- Inserts each prompt into the Flow editor
- Clicks the **Generate** button
- Monitors generation progress via tile DOM analysis
- Automatically downloads the completed output

### Architecture
| File | Role |
|---|---|
| `scripts/content.js` | Main automation logic, injected into the Flow page |
| `scripts/background.js` | Service worker — message routing, download management, CDP handler |
| `panel/sidepanel.js` | Side panel UI — settings, prompt input, start/stop control |
| `panel/sidepanel.html/css` | Side panel HTML/CSS |
| `manifest.json` | Extension manifest (MV3) |

## 2. Initial Problem Report

The user reported that the **Generate button click was not working** — the automation appeared to run (logging "clicking generate button") but nothing actually happened. Generation never started, and the automation timed out at `waitForGenerationComplete`.

### Observed Symptoms
- Log: `Waiting for generation to complete` → `Timed out waiting for new tiles to appear`
- No new tile appeared in the Flow project after the automation "clicked" Generate
- Manually pressing Enter or clicking Generate by hand worked perfectly
- The user confirmed: *"generate kedua dan ketiga itu aku hit generate MANUAL pas masih di posisi stuck"* — meaning the successful runs were manual, not automated

## 3. Investigation Path

### Phase 1 — Subagent Browser Inspection

A browser subagent was deployed to navigate to the actual Flow project URL and inspect:
- The Slate editor DOM structure
- The Generate button attributes and React props
- What happened when the button was clicked via Chrome DevTools Protocol (CDP)

**Subagent finding:** The subagent succeeded in clicking Generate using CDP (`Input.dispatchMouseEvent`), which generates events with `isTrusted: true`. The same approach was NOT possible from a content script using `dispatchEvent()`.

### Phase 2 — Root Cause Analysis

**Root cause identified:** The Flow editor is built on **Slate.js** (a React-based rich text editor framework). Slate validates the `isTrusted` property on input events before processing them.

| Method | `isTrusted` | Result |
|---|---|---|
| Real user keyboard/mouse | `true` | ✅ Works |
| Chrome DevTools Protocol (CDP) | `true` | ✅ Works |
| `element.click()` | `false` | ❌ Ignored by Slate |
| `new MouseEvent(...)` + `dispatchEvent()` | `false` | ❌ Ignored by Slate |
| `document.execCommand("insertText")` | `false` | ❌ Inserts into DOM only, not Slate state |
| `new KeyboardEvent(...)` + `dispatchEvent()` | `false` | ❌ Ignored by Slate |
| `new InputEvent("beforeinput")` | `false` | ❌ Slate checks trusted for some paths |
| React Fiber `onClick` traversal | N/A | ❌ No onClick found — button is a form submit |

**Key insight:** `execCommand("insertText")` was inserting text into the raw DOM but **not** into Slate's internal React state. When the Generate button was clicked, Slate used its own (empty/stale) state — not the DOM — resulting in a no-op generation request.

### Phase 3 — Attempted Approaches That Failed

1. **`document.execCommand("insertText")`** — Updates DOM only, bypasses Slate state
2. **`ClipboardEvent("paste")`** — Slate ignores untrusted paste events
3. **`InputEvent("beforeinput", { inputType: "insertText" })`** — Attempted as last resort; unreliable
4. **React Fiber `onClick` traversal** — Generate button uses form submit, not a direct onClick; traversal returned `false`
5. **`document.activeElement.blur()`** — This was discovered to *break* Slate's focus state, making things worse; it was removed
6. **`form.requestSubmit()`** — Form element was not found in the DOM tree reliably
7. **Ctrl+A + Delete via keyboard events** — `isTrusted: false`, Slate ignores it
8. **`new KeyboardEvent("keydown", { key: "Enter" })`** on editor — `isTrusted: false`, ignored

## 4. Final Solution — Chrome DevTools Protocol (CDP)

### How CDP Works

The `chrome.debugger` API allows a Chrome extension to communicate with the Chrome DevTools Protocol at the browser engine level. Events dispatched via CDP are **generated by the browser itself**, not by JavaScript — therefore they always have `isTrusted: true`.

### Implementation

#### `manifest.json`
Added the `"debugger"` permission:
```json
"permissions": ["storage", "scripting", "activeTab", "tabs", "sidePanel", "downloads", "clipboardWrite", "debugger"]
```

#### `scripts/background.js`
Added a `cdp:action` message handler with three actions:

| Action | CDP Commands Used | Purpose |
|---|---|---|
| `insertText` | `Input.dispatchMouseEvent` (click to focus) → `Input.dispatchKeyEvent` (Ctrl+A) → `Input.insertText` | Insert text into Slate editor with proper state update |
| `click` | `Input.dispatchMouseEvent` (mouseMoved + mousePressed + mouseReleased) | Click the Generate button as a trusted browser event |
| `pressEnter` | `Input.dispatchMouseEvent` (click to focus) → `Input.dispatchKeyEvent` (Enter keyDown + keyUp) | Submit via keyboard as trusted event |

Added helper functions:
- `cdpSend(debuggee, method, params)` — Promise wrapper around `chrome.debugger.sendCommand`
- `sleep(ms)` — Promise-based delay for CDP command sequencing

#### `scripts/content.js`

**`setPromptText(text)` — Rewritten:**
- **Strategy 1 (Primary):** CDP `insertText` — clicks editor center, Ctrl+A to select all, `Input.insertText` to replace. This updates Slate's React state correctly.
- **Strategy 2 (Fallback):** `execCommand("insertText")` — kept as fallback
- **Strategy 3 (Last resort):** `ClipboardEvent("paste")` and `InputEvent("beforeinput")`

**`triggerGenerate()` — Rewritten:**
- **Strategy 1:** CDP `click` on the Generate button center coordinates
- **Strategy 2:** CDP `pressEnter` on the Slate editor (fallback if click fails)
- Removed: DOM `click()`, `dispatchEvent()`, keyboard simulation (all `isTrusted: false`)

## 5. Additional Fixes Applied

### 5.1 Removed `document.activeElement.blur()`
**Problem:** An earlier version called `blur()` before clicking Generate, which caused Slate to lose focus state and the submission to be ignored even when clicked manually.  
**Fix:** Removed the `blur()` call entirely.

### 5.2 Queued Video False-Positive Detection
**Problem:** When generating video, Flow sometimes shows a tile in "Queued" state. During queueing, the tile briefly shows `layerOpacity: 1, blurAmount: 0` (which looks like "complete") before reverting to `layerOpacity: 0, blurAmount: 80` (still generating). The extension was falsely declaring generation complete and proceeding to download a non-existent result.

**Fix:** Added **double-confirmation** logic in `waitForGenerationComplete`:
```javascript
if (allDone) {
    await delay(GENERATION_POLL_MS);
    // Re-check all tiles
    const confirmTiles = getNewTiles(existingTileIds);
    let confirmedAllDone = true;
    for (const t of confirmTiles) {
        if (getTileStatus(t) === "generating") {
            confirmedAllDone = false;
            break;
        }
    }
    if (!confirmedAllDone) {
        // Was a Queued false-positive — continue monitoring
        continue;
    }
    // Real completion confirmed
}
```

### 5.3 Tile Layer Log Spam Reduction
**Problem:** `getTileStatus()` was called on every poll interval (~2s), and it logged `"Tile layer analysis"` on every call regardless of whether anything changed. This produced 10–15 identical log lines per generation.

**Fix:** Added a state cache (`getTileStatus._stateCache`) on the function itself. Logs (`"Tile layer changed"`) only fire when `layerOpacity` or `blurAmount` changes between polls.

**Before:**
```
Tile layer analysis {opacity: 0, blur: 80}  ← repeated 9×
Tile layer analysis {opacity: 1, blur: 15}
Tile layer analysis {opacity: 1, blur: 0}
Tile layer analysis {opacity: 1, blur: 0}   ← repeated after complete
```

**After:**
```
Tile layer changed {opacity: 0, blur: 80}
Tile layer changed {opacity: 1, blur: 15}
Tile layer changed {opacity: 1, blur: 0}
```

### 5.4 Debug Logging Added to `setPromptText`
Added entry log at the very top of `setPromptText`:
```javascript
console.log(LOG_PREFIX, "setPromptText called", { textLength: ..., preview: ... });
```
This was critical for identifying that `setPromptText` was being called with correct text but the insertion was silently failing.

## 6. Key Technical Learnings

### 6.1 Slate.js and `isTrusted`
Slate.js (the rich text editor used by Google Labs Flow) validates `event.isTrusted` on:
- Mouse events used to focus/click
- Keyboard events used to trigger submission
- Input events used to insert text

Any programmatic event from JavaScript (content scripts, injected code) has `isTrusted: false` and is **silently ignored** by Slate in security-sensitive code paths.

### 6.2 `execCommand` vs Slate State
`document.execCommand("insertText")` operates on the raw DOM `contenteditable` element. Slate.js maintains its own **virtual document model** separate from the DOM. DOM manipulation via `execCommand` can appear to work (text shows in the UI) but Slate's internal state remains unchanged. When the form is submitted, Slate uses its internal state — not the DOM — resulting in an empty or stale prompt being sent to the API.

### 6.3 CDP Is the Only Reliable Path from a Content Script
From a Chrome extension content script, the only way to produce `isTrusted: true` events is via `chrome.debugger` → CDP. This requires:
1. `"debugger"` permission in `manifest.json`
2. A background service worker to handle `chrome.debugger.attach/sendCommand/detach`
3. Coordinate calculation in the content script (using `getBoundingClientRect()`)

**Side effect:** Chrome shows a `"[Extension] started debugging this browser"` banner while the debugger is attached. This can be suppressed system-wide by launching Chrome with `--silent-debugger-extension-api`, but this cannot be done from within the extension itself.

### 6.4 React Fiber Traversal Limitation
The Generate button's click handler is not directly on the button element — it is handled via React's event delegation from a parent form's `onSubmit`. Traversing `__reactFiber$` up the fiber tree found no `onClick` on the button or its immediate ancestors. This approach was abandoned.

## 8. Current Working State

The automation pipeline now works end-to-end for both **text-to-image** and **text-to-video** modes:

```
Start → Configure Settings → Tile Snapshot
     → CDP insertText (prompt into Slate state) ✅
     → Find Generate Button → CDP click ✅  
     → Wait for tile → Monitor opacity/blur changes (log on change only) ✅
     → Double-confirm completion (handles Queued state) ✅
     → Download result → Clear editor → Next prompt
```
